# spec 확인 스킬(`spec-check`): 요청의 규모를 판정해 작업 방식을 고른다

## Context
- 지금 CLAUDE.md 규칙은 "여러 파일을 바꾸는 작업은 plan mode"뿐입니다. 언제 계획을 세우는지가 막연해서, 작은 일에도 계획 절차를 거치거나 반대로 큰 일을 바로 시작할 수 있습니다.
- 사용자 제안: 요청을 받으면 **먼저 spec을 확인**하고, 작으면 바로 수정하고 크면 계획 스킬로 task를 나눠 진행합니다. 판정은 **3단계(작음/중간/큼)**로 하기로 했습니다.
- 핵심 원칙은 **"요청의 크기와 변경의 크기는 다르다"**입니다. 예를 들어 "메뉴 '행사'를 '행사 안내'로"는 한 줄짜리 요청이지만, 실제로는 `navigation.ts`, `e2e/navigation.spec.ts`, 페이지 제목(모호함)에 걸립니다. 그래서 요청 문장만 보지 않고 **영향 범위를 먼저 찾은 뒤** 판정합니다.
- 6축으로는 계획(PL: 언제 계획하나), 구조(ST-06: Skill), 개선(IM-02: 반복을 Skill로)에 해당합니다. 이 스킬은 계획 스킬의 앞단이고, 계획 스킬은 다음 작업에서 만듭니다.

## 확인한 사실
- **skill-creator 절차:** 초안 → 실제 요청 예시로 시험(스킬 있을 때와 없을 때 비교) → 결과 비교 화면 → 사용자 검토 → 개선. description은 "언제 쓰는지"를 적극적으로 적어야 덜 놓칩니다.
- **도구:** Python 3.11과 결과 비교 화면 생성기(`eval-viewer/generate_review.py`)가 있습니다. `.claude/skills/`는 아직 없습니다.
- **시험용 사실:**
  - "행사"는 `src/lib/navigation.ts`, `src/app/events/page.tsx`(제목 2곳), `e2e/navigation.spec.ts`(메뉴 명세, 탭 제목 테스트)에 있습니다. `HeroBanner.tsx`의 "행사와 소식"은 메뉴가 아닙니다.
  - 히어로 설명 문구는 e2e 테스트가 검사하지 않습니다. 고쳐도 테스트에 영향이 없습니다.

## 만들 것

### 1. `.claude/skills/spec-check/SKILL.md`
- **description (트리거):** 코드·설정·문서 구조를 바꾸는 요청을 받으면 구현 전에 먼저 쓴다. 이름 바꾸기나 문구 수정처럼 작아 보이는 요청에도 쓴다. 작아 보여도 테스트나 다른 화면에 걸릴 수 있기 때문이다. 질문 답변이나 설명 요청에는 쓰지 않는다.
- **본문 절차:**
  1. **spec 정리:** 무엇을 / 어디서 / 완료 조건을 한 줄씩
  2. **영향 범위 조사:** 규모에 비례해서, 작은 요청이면 검색 한두 번. 확인 대상은 아래와 같습니다.
     - 같은 문자열·식별자 (`src/`, `e2e/`)
     - 테스트 명세 (`e2e/`)
     - 페이지 제목·metadata
     - 데이터 계층 (`src/lib/data`, `mock`, `types`)
     - 하네스 파일 (`CLAUDE.md`, `.claude/`, `.husky/`)
     - `docs/lessons.md`의 관련 함정
     - 다른 세션이 남긴 변경 (`git status`)
  3. **모호한 점 질문:** 결과가 달라지는 것만 묻습니다. 예: "메뉴 이름만인가요, 페이지 제목도인가요?"
  4. **규모 판정 표** (가장 큰 쪽을 따름):

     | 기준 | 작음 | 중간 | 큼 |
     |---|---|---|---|
     | 동작 | 그대로 (문구, 색, 오타) | 그대로이거나 작은 조정 | 새 화면·동작, 데이터 구조 |
     | 영향 범위 | 1~2곳, 다 찾음 | 3~5곳, 또는 테스트 수정 동반 | 여러 영역, 또는 범위를 다 못 찾음 |
     | 모호함 | 없음 | 질문 1~2개로 해결 | 요구사항 자체를 정해야 함 |
     | 의존성·설정 | 없음 | 없음 | 새 라이브러리, 설정 변경 |
     | 하네스 | 안 건드림 | 문구만 | hook·권한·규칙의 동작 변경 |
     | 되돌리기 | 쉬움 | 쉬움 | 어려움 (데이터, 배포, 외부 서비스) |

  5. **판정 보고 (짧은 고정 형식):** spec / 영향 범위 / 확인할 점 / 판정과 이유 한 줄 / 다음 행동
  6. **다음 행동:**
     - **작음:** 보고하고 바로 수정합니다. 확인할 점이 없으면 기다리지 않습니다. DoD는 hook이 지킵니다.
     - **중간:** 3~5줄 계획(바꿀 파일과 순서, 확인 방법)을 보여 주고 확인받은 뒤 진행합니다. 계획서는 저장하지 않고, 달라진 점은 커밋 메시지에 남깁니다.
     - **큼:** plan mode로 계획을 세웁니다. 승인받으면 `docs/plans/`에 저장하고 task로 나눠 하나씩 진행·검증합니다. 계획 스킬이 생기면 그 스킬로 넘깁니다.
  7. **재판정:** 진행 중에 영향 범위가 판정보다 커지면 멈추고 다시 판정해 알립니다.
- **예시 3개(이 프로젝트 기준):** 메뉴 이름 변경(중간, 질문 1개), 히어로 문구 오타(작음), 통계 카드 추가(큼)
- **지름길 경고 표 (팀 스킬의 Red Flags 형식):**
  - "이름만 바꾸면 되니 검색 생략" → 테스트가 깨져 커밋이 거부됨
  - "작으니 물어볼 것 없음" → 모호하면 묻기
  - "빨리 하려고 큼을 중간으로" → 판정 기준표를 따름
  - "한 줄이라 하네스도 작음" → hook·권한의 동작이 바뀌면 큼

### 2. `CLAUDE.md` 규칙 교체
현재: "여러 파일을 바꾸는 작업은 plan mode로 계획을 세우고, 모호한 요구사항은 먼저 질문한 뒤, 승인 후 구현한다."
→ 변경: "코드나 설정을 바꾸는 요청은 먼저 `spec-check` 스킬로 영향 범위를 찾고 작음·중간·큼으로 판정한다. 큼은 plan mode로 계획을 세우고 승인 후 구현하며, 모호한 요구사항은 먼저 질문한다."
- "plan mode" 문구가 남아 있어 진단의 계획 규칙(PL-03)도 그대로 충족합니다.

### 3. 시험 (skill-creator 방식, 가볍게)
- 실제 요청 4개를 **스킬 있음 / 없음** 두 조건으로 subagent 8개가 동시에 실행합니다. 모두 **읽기 전용**이고 "파일을 고치지 말고 무엇을 할지 보고만 하라"고 지시합니다.
