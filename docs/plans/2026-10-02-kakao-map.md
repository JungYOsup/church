# 홈 지도 칸 카카오맵 연동과 Vitest TDD 도입

## Context
- 왜 하는가: 홈 두 번째 행의 지도 칸은 지금 대체 화면뿐입니다. 상위 계획서의 카카오맵 절(교회 마커, 이름 라벨, "현재 지도 범위 내 교회 N개", 키가 없으면 대체 화면)을 홈 지도 칸에 구현합니다. 처음으로 순수 로직(지도 범위 안 교회 고르기)이 생기므로, 이 로직은 Vitest를 들여 테스트를 먼저 쓰고 실패를 확인한 뒤 구현합니다(TDD). 이번 경험을 보고 plan-work 템플릿에 TDD 규칙을 넣을지 정합니다.
- spec:
  - 무엇을: 홈 지도 칸에 카카오맵, 교회 15곳의 마커와 이름, 지도 범위 안 교회 수. 키가 없거나 SDK를 불러오지 못하면 지금의 대체 화면
  - 어디서: 홈 "우리 지역 교회 지도" 칸 (`/map` 페이지는 이번 범위 밖)
  - 완료 조건:
    - 개발 서버에서 마커가 보이고, 지도를 움직이면 범위 내 교회 수가 바뀝니다.
    - 범위 필터는 테스트를 먼저 써서 실패한 출력이 남아 있습니다.
    - `npm run test`(단위 + e2e)가 통과합니다.
- 6축 위치: 검증(단위 테스트 추가, VF-01·VF-04), 실행(TDD를 run-plan 증거로)

## 확인한 사실
- **상위 계획서 카카오맵 절(82~88행, 통째로 읽음):**
  - 변수는 `NEXT_PUBLIC_KAKAO_MAP_KEY`이고, `.env.example`도 함께 둡니다.
  - SDK는 `next/script`로 `autoload=false`를 붙여 불러오고, `kakao.maps.load()` 뒤에 그립니다. 래퍼 라이브러리를 쓸지는 구현할 때 정하기로 되어 있습니다.
  - 마커는 십자가 핀과 이름 라벨입니다. 선택한 교회의 사진 오버레이는 이번 범위 밖입니다.
  - `idle` 이벤트에서 범위 안 교회를 걸러 "현재 지도 범위 내 교회 N개"를 보여 줍니다. 키가 없으면 정적 대체 화면을 보여 줍니다.
- **참고 디자인:** 참고 이미지의 지도 칸에는 파랑·초록 핀과 교회 이름 라벨이 있습니다. 오른쪽에 +/- 확대 버튼, 왼쪽 아래에 흰 알약 모양의 "📍 현재 지도 범위 내 교회 24개"가 있습니다.
- **Next.js(설치된 문서):**
  - `NEXT_PUBLIC_` 변수는 `next build` 때 번들에 값이 고정됩니다(`02-guides/environment-variables.md` 156~166행).
  - 값을 찾는 순서는 `process.env` → `.env.$(NODE_ENV).local` → `.env.local`입니다(268행). 그래서 테스트 서버에 다른 값을 주면 `.env.local`을 덮습니다.
  - Script의 `onReady`는 처음 로드할 때와 컴포넌트가 다시 마운트될 때마다 실행됩니다. `onError`도 있고, 둘 다 클라이언트 컴포넌트에서만 동작합니다(`03-api-reference/02-components/script.md` 303~307행, 398~400행).
  - Vitest 가이드는 컴포넌트 테스트를 위해 jsdom과 Testing Library를 함께 설치합니다. 비동기 서버 컴포넌트는 Vitest가 지원하지 않아 e2e를 권합니다(`02-guides/testing/vitest.md`).
- **카카오맵 API(ctx7 `/websites/apis_map_kakao_web`):**
  - `autoload=false`로 불러온 뒤 `kakao.maps.load(callback)`에서 객체를 씁니다.
  - `LatLngBounds.contain`은 북동쪽 꼭짓점과 같은 점을 `false`로 돌려줍니다. 경계를 어떻게 다룰지는 우리 함수에서 정합니다.
  - `kakao.maps.event.addListener(map, "idle", fn)`, `CustomOverlay({ position, content, yAnchor })`, `setMap(map | null)`을 씁니다.
- **래퍼 라이브러리:** `react-kakao-maps-sdk` 1.2.2는 React 19를 지원하고 2026-08에 갱신되었습니다(npm). 다만 안에서 어떤 카카오 API를 부르는지 우리가 정하지 못해, e2e용 가짜 SDK를 만들기 어렵습니다.
- **Vitest:**
  - 5.0.3이 최신이고 Node `^22.12`가 필요합니다. 우리는 22.14입니다.
  - 기본 범위는 `**/*.{test,spec}.?(c|m)[jt]s?(x)`라서 그대로 두면 `e2e/*.spec.ts`도 잡습니다. 그래서 `test.include`로 `src`만 지정해야 합니다.
  - 별칭은 `resolve.alias`나 `test.alias`에 `resolve(import.meta.dirname, …)`로 줍니다. 한 번만 실행하려면 `vitest run`입니다(ctx7 `/websites/main_vitest_dev`).
- **기존 설정과의 충돌(조사로 찾음):**
  - `tsconfig.json`의 include가 `**/*.ts`와 `**/*.mts`라서, `next build`가 테스트 파일과 `vitest.config.mts`도 타입 검사합니다. 그래서 vitest를 devDependency로 설치해야 합니다.
  - `.husky/pre-commit`의 `APP_FILES`와 `.claude/hooks/verify-on-stop.sh`의 `APP_PATHS`에 Vitest 설정 파일이 없습니다. 그 파일만 바꾼 커밋에서는 검사가 돌지 않으므로 둘 다 더해야 합니다.
  - 테스트 서버도 `next build`를 하므로 `.env.local`의 실제 키가 들어갑니다. 그러면 테스트마다 카카오 서버에 요청이 갑니다. 3100 포트는 카카오에 등록하지 않았으니 실패하고, 콘솔 오류 fixture가 홈 테스트 전부를 실패시킵니다.
  - 지금의 e2e "지도를 띄울 수 없으면 대체 화면을 보여 준다"는 키가 있는 빌드에서 깨집니다.
- **관례:**
  - 데이터는 `getChurches()`로 서버 컴포넌트에서 받습니다(`src/lib/data/churches.ts`).
  - 테스트 기대값은 앱 코드에서 가져오지 않습니다.
  - 콘솔 오류가 나면 실패하는 auto fixture가 있습니다(`e2e/fixtures.ts`).
- **배운 점:**
  - Tailwind는 TS 파일 안 문자열의 클래스도 찾습니다(통계 카드).
  - 새 파일의 클래스가 개발 서버 CSS에 빠지면 빌드 CSS와 비교합니다.
  - `.env.local`은 읽지 않습니다(권한 규칙 `Read(./.env*.local)` 차단).
- **사용자 확인:** 범위는 홈 지도 칸만으로 정했습니다. 카카오 설정(도메인 등록, 카카오맵 사용, 변수 이름)은 아직 일부가 남아 있습니다.

## 결정
- **질문과 답:**
  - 범위: 홈 지도 칸만(`/map` 페이지는 다음 작업)
  - 카카오 설정: 일부 미완. 키가 필요 없는 TDD task를 앞에 두고, 지도 task(T2) 직전에 설정을 다시 확인합니다.
- **정한 것:**
  - **래퍼 없이 SDK를 직접 씁니다.** `next/script`와 우리가 쓰는 API만 담은 타입 선언(`src/types/kakao.d.ts`)으로 만듭니다. 쓰는 API가 적고(지도, LatLng, 범위, CustomOverlay, 확대 버튼, idle), 그 목록을 우리가 정해야 e2e의 가짜 SDK가 같은 범위만 흉내 낼 수 있습니다. 새 런타임 의존성도 생기지 않습니다.
  - **Vitest만 설치합니다.** 테스트할 것이 순수 함수뿐이라 jsdom과 Testing Library는 컴포넌트 단위 테스트가 필요해질 때 더합니다. 설정은 `environment: "node"`, `include: ["src/**/*.test.ts"]`, `@` 별칭입니다.
  - **스크립트:** `test:unit`은 `vitest run`이고, `test`는 `test:unit && test:e2e`입니다. 그래서 pre-commit에서도 단위 테스트가 돕니다.
  - **범위 필터는 `src/lib/geo.ts`의 순수 함수입니다.**
    - `filterWithinBounds(items, bounds)`는 `{ lat, lng }`를 가진 항목 중 범위 안의 것을 원래 순서와 원래 객체 그대로 돌려줍니다.
    - 경계 위의 점은 포함합니다. 지도 가장자리에 걸친 핀도 화면에 보이므로 셉니다.
    - 15곳은 서버의 `MapPreview`가 `getChurches()`로 받아 이름과 좌표만 넘기고, 클라이언트가 `idle` 때마다 걸러 셉니다. `getChurches({ bounds })`는 데이터베이스 조회가 필요해지는 `/map`·Supabase 단계에서 더합니다.
  - **처음 화면:** 서울시청(37.5665, 126.978)을 중심으로 확대 수준 8에서 시작합니다. 서울 교회가 대부분 보이는 범위입니다. 실제 화면을 보고 조정하면 변경 이력에 적습니다.
  - **핀:** `CustomOverlay`에 DOM 노드를 넣습니다. 파란 원 안의 흰 십자가와 흰 알약 모양의 이름 라벨이고, `data-church-pin` 속성을 붙입니다. 이름은 `textContent`로 넣어 HTML로 해석되지 않게 합니다.
  - **교회 수 표시:** 지도 왼쪽 아래에 "현재 지도 범위 내 교회 N개"를 둡니다(목업 문구). 지도를 움직이면 바뀌므로 `aria-live="polite"`를 줍니다.
  - **그 밖의 지도 동작:** 카카오 `ZoomControl`을 오른쪽에 둡니다. 칸 크기가 바뀌면 `ResizeObserver`로 `map.relayout()`을 부릅니다.
  - **대체 화면을 보여 주는 경우:** ① 서버에서 키가 없을 때 ② SDK 스크립트 `onError` ③ `onReady`인데 `window.kakao`가 없을 때. 불러오는 동안에는 연한 바탕에 "지도를 불러오는 중"을 보여 줍니다.
  - **e2e는 카카오 서버에 기대지 않습니다.**
    - `playwright.config.ts`의 `webServer.env`로 가짜 키를 넣어 빌드합니다. `.env.local`이 있든 없든 같은 결과가 나오고, 실제 키는 테스트에 쓰이지 않습니다.
    - `e2e/fixtures.ts`의 auto fixture가 `dapi.kakao.com` 요청을 가짜 SDK(`e2e/fake-kakao-sdk.js`)로 바꿉니다. 가짜 SDK는 우리가 쓰는 API만 흉내 냅니다. 오버레이를 지도 칸에 실제 DOM으로 붙이고, 테스트가 범위를 바꾸고 `idle`을 일으킬 수 있습니다.
    - 대체 화면 테스트는 SDK 요청을 막아(`abort`) 확인합니다. 이때 나는 "Failed to load resource" 콘솔 오류는 그 테스트에서만 허용합니다(fixture에 `allowedConsoleErrors` 옵션을 더함).
  - **`.env.example`:** 변수 이름과 설명만 적습니다(CLAUDE.md 규칙).

## 리스크와 멈출 조건
- **카카오 설정 미완:** 도메인이나 카카오맵 사용 설정이 안 되어 있으면 지도가 그려지지 않습니다. T2 시작 조건에서 확인합니다. 설정을 마쳤는데도 지도가 안 뜨면 콘솔과 네트워크 응답으로 원인을 찾습니다. SDK는 로드됐는데 지도만 실패하는 경우를 대체 화면으로 보낼 방법(시간 제한 등)이 필요하면 계획 밖 결정이므로 묻습니다.
- **빈 값으로 덮어써지지 않음:** `NEXT_PUBLIC_KAKAO_MAP_KEY=`(빈 문자열)가 `.env.local`을 덮지 못하면 키 없는 빌드를 만들 수 없습니다. 그때는 이 확인을 코드 검토와 변경 이력으로 대신합니다. `.env.local`은 읽거나 옮기지 않습니다.
- **Vitest와 Node 버전:** Vitest 5는 Node 22.12 이상이 필요합니다. hook은 nvm으로 22.14를 쓰므로 문제없습니다. 시스템 Node 18에서 직접 돌리면 실패합니다.
- **가짜 SDK와 실제 SDK가 어긋남:** 가짜 SDK는 우리가 쓰는 API만 흉내 냅니다. 실제 동작은 T2에서 진짜 키로 확인한 것을 근거로 삼습니다.
- **계획 밖 결정이 필요할 때:** 범위·데이터 구조 변경, 새 의존성, 되돌리기 어려운 작업이 필요해지면 다음 task로 넘어가지 않고 묻습니다.
