# README와 CI: 저장소 첫 화면과 push마다 자동 검증

## Context
- **왜 하는가:** 공개 URL(https://church-community-eight.vercel.app)이 생겼지만, 공개 저장소의 README는 `# church` 한 줄뿐입니다. 포트폴리오를 보는 사람이 처음 만나는 곳이 비어 있습니다. 검증은 응답 종료(Stop hook)와 커밋(pre-commit) 때 이 컴퓨터에서만 돕니다. 그래서 GitHub에 올라간 코드가 테스트를 통과했는지는 보이지 않습니다. 상위 계획서 3단계("README: 스크린샷, 아키텍처…")와, 그동안 "배포할 때"로 미뤄 둔 CI(`2026-10-01-e2e-tests.md` 63행, `2026-10-01-pre-commit-e2e.md` 59행)를 이번에 합니다.
- **spec**
  - 무엇을:
    - README를 새로 씁니다: 운영 링크, 스크린샷, 주요 기능, 기술 스택, 구조, 실행·테스트 방법, 개발 방식(짧은 절)
    - GitHub Actions CI: push와 PR마다 lint → 단위 테스트 → e2e(빌드 포함)
  - 어디서: `README.md`, `.github/workflows/ci.yml`(새 파일), `docs/screenshots/`(새 폴더), GitHub 저장소 정보(About)
  - 완료 조건:
    - GitHub 저장소 첫 화면에 README가 스크린샷·운영 링크·CI 배지와 함께 보입니다.
    - CI가 GitHub에서 실제로 돌아 초록색이 됩니다.
    - 일부러 깨뜨린 커밋에서는 CI가 빨간색이 됩니다.
- **6축 위치:** 검증(VF-04 자동 검증: CI), 맥락(README가 프로젝트 소개 문서)

## 확인한 사실
- **README:** 지금 내용은 `# church`가 전부입니다. `.github` 폴더는 없습니다.
- **GitHub 러너:** `ubuntu-latest`(Ubuntu 24.04) 이미지에 Google Chrome 154와 Node 22.23이 깔려 있습니다(actions/runner-images `Ubuntu2404-Readme.md`). `playwright.config.ts`는 설치된 Chrome(`channel: "chrome"`)을 쓰므로 Playwright 브라우저를 따로 받지 않아도 됩니다.
  - **조사로 바뀐 점:** 배운 점 126행과 e2e 계획서는 "CI에서는 `npx playwright install chrome`이 필요하다"고 적었습니다. 이 설치 단계는 빼고 시작합니다. 첫 실행에서 Chrome을 찾지 못하면 그때 `npx playwright install --with-deps chrome`을 넣습니다.
- **액션 최신 버전**(`gh api repos/<액션>/releases/latest`): `actions/checkout` v7.0.1, `actions/setup-node` v7.0.0, `actions/upload-artifact` v7.0.1. Playwright 1.63 문서(ctx7 `/microsoft/playwright/v1.63.0` ci-intro)의 예시는 `npm ci` → `npx playwright install --with-deps` → `npx playwright test` → `if: ${{ !cancelled() }}` 결과물 올리기입니다.
- **e2e 실행 조건:**
  - `playwright.config.ts`의 `webServer`가 가짜 카카오 키로 `npm run build && npm run start -p 3100`을 합니다. 빌드는 e2e 안에서 한 번 일어납니다.
  - 카카오 SDK 요청은 fixture가 가짜로 돌려주므로 비밀값이나 외부 서버가 필요 없습니다.
  - `forbidOnly`·`retries` 설정은 없습니다. `workers: 3`, `trace: "retain-on-failure"`(실패하면 `test-results/`에 남음)입니다.
- **시간대:** e2e 코드에는 `new Date`·`Date.now`·시간대 의존이 없습니다(grep). 단위 테스트는 `vitest.config.mts`가 TZ를 UTC로 고정합니다. 러너가 UTC여도 결과가 같습니다.
- **git hook:** `npm ci`가 `prepare`(husky)를 돌리지만, 러너에는 `.git`이 있어 hook 경로만 설정하고 끝납니다. pre-commit의 검사 대상(`APP_FILES`)에 `.github/`는 없습니다. 워크플로만 바뀐 커밋은 로컬 테스트를 건너뛰고, 대신 CI가 검사합니다.
- **스크린샷:** 운영 사이트만 진짜 카카오맵이 뜹니다(로컬 테스트 빌드는 가짜 키). 배운 점 "전체 페이지 스크린샷은 화면 크기를 바꾼다"에 따라 `fullPage` 대신 화면 높이를 키워 찍습니다. scratchpad 스크립트는 Playwright를 절대 경로로 가져옵니다(배운 점).
- **상위 계획서 3단계:** "README: 스크린샷, 아키텍처 다이어그램, ERD, RLS 설계에서 고민한 점". ERD와 RLS는 Supabase가 없어 아직 쓸 수 없습니다.
- **사진 출처:** 교회·행사 사진 12장은 Unsplash License이고, 출처가 상위 계획서 변경 이력(2026-10-02)에 있습니다.

## 결정
- **질문과 답:** README에 AI 하네스 개발 방식을 넣을지 물었고, 사용자가 "짧은 절로 소개"를 골랐습니다(5~8줄, docs 링크).
- **정한 것:**
  - **README는 한국어로 씁니다.** 구성: 제목·한 줄 소개·CI 배지·운영 링크 → 스크린샷 → 주요 기능(목데이터 데모라는 점 명시) → 기술 스택 → 구조(폴더 요약, 데이터 흐름 Mermaid 그림) → 시작하기(`nvm use`, `npm install`, `.env.local`, `npm run dev`) → 테스트 → 개발 방식 → 로드맵(1단계 UI ✓, 배포 ✓, 2단계 Supabase) → 사진 출처
  - **스크린샷 4장:** `docs/screenshots/`에 JPEG(quality 80)로 둡니다. 운영 사이트의 홈 데스크톱(1440px, 높이를 키워 세 번째 행까지), 지도 데스크톱(1440×900), 홈·지도 모바일(375×812, 선명하게 2배율). 한 장에 300KB 이하가 목표입니다.
  - **CI(`.github/workflows/ci.yml`):**
    - 모든 branch의 push와 PR에서 돕니다. `concurrency`로 같은 branch의 이전 실행은 취소합니다. `permissions: contents: read`, 제한 시간 20분입니다.
    - 단계: `checkout@v7` → `setup-node@v7`(`node-version-file: .nvmrc`, `cache: npm`) → `npm ci` → `npm run lint` → `npm run test:unit` → `npm run test:e2e`. 실패하면 `upload-artifact@v7`로 `test-results/`(trace)를 올립니다.
    - 빌드 단계를 따로 두지 않습니다. e2e가 빌드한 결과로 테스트하기 때문입니다.
  - **`playwright.config.ts`에 `forbidOnly: !!process.env.CI`를 더합니다.** `test.only`를 남긴 채 커밋하면 로컬에서는 그 테스트 하나만 돌고 통과해, pre-commit이 잡지 못합니다. CI에서는 실패하게 합니다.
  - **`retries`와 `workers`는 바꾸지 않습니다.** 로컬과 CI 조건을 같게 둡니다. CI에서 흔들림이 나면 배운 점대로 사용자에게 물어 정합니다.
  - **저장소 About에 운영 링크와 설명을 넣습니다**(`gh repo edit --homepage --description`).
  - **git:** branch `chore/readme-ci`에서 task마다 커밋합니다. T1부터 branch를 push해 CI를 실제로 돌리고, 마지막에 `--no-ff` merge한 뒤 master를 push합니다. 깨뜨려 보기는 버리는 branch에서 하고, 확인 뒤 원격과 로컬에서 지웁니다. 승인하시면 이 push들과 저장소 정보 변경도 승인한 것으로 봅니다.

## Tasks
- [ ] **T1. CI 워크플로와 `forbidOnly`**
  - 파일: `playwright.config.ts`, `.github/workflows/ci.yml`
  - 의존: 없음
  - 테스트 먼저(red): `e2e/home.spec.ts`의 한 테스트를 잠깐 `test.only`로 바꾸고 `CI=1 npx playwright test --list`를 돌립니다. 지금은 오류 없이 목록이 나옵니다(red: CI에서 `.only`를 막지 못함). `forbidOnly`를 넣은 뒤에는 `.only` 금지 오류가 나야 합니다. 확인한 뒤 `test.only`를 되돌립니다.
  - 확인(동작 증거):
    - 커밋하고 `chore/readme-ci`를 push한 뒤 `gh run watch`: 워크플로가 success이고, 로그에 lint 통과, `Tests 90 passed`, `151 passed`가 있습니다.
    - 버리는 branch에 `test.only` 하나를 커밋해 push합니다. 로컬 pre-commit은 통과하지만 CI는 e2e 단계에서 `forbidOnly` 오류로 failure가 나고 `test-results`를 올리는지 봅니다. 확인 뒤 그 branch를 원격·로컬에서 지웁니다.

## 리스크와 멈출 조건
- **러너에서 Chrome을 못 찾는 경우:** `npx playwright install --with-deps chrome` 단계를 넣고 변경 이력에 적습니다.
- **CI에서만 e2e가 흔들리는 경우**(러너가 이 컴퓨터보다 약함): 실패한 테스트와 trace를 보고, 같은 커밋을 다시 돌려 재현되는지 확인합니다. 설정(workers, retries, actionTimeout)을 바꿔야 하면 사용자에게 묻습니다.
- **CI 결과가 로컬과 다른 경우**(시간대, 글꼴, 경로 대소문자): trace와 로그로 원인을 하나씩 확인해 고칩니다. 앱 동작을 바꿔야 하면 묻습니다.
- **운영 사이트 스크린샷에 지도가 덜 그려진 경우:** 기다리는 시간을 늘려 다시 찍습니다.
- 계획 밖 결정(유료 기능, 브랜치 보호 규칙, 테스트 설정 변경)이 필요해지면 다음 task로 넘어가지 않고 묻습니다.

## 검증
- 전체 완료 조건: `npm run lint && npm run build`, `npm run test` 통과, master의 CI success, 저장소 첫 화면에 README
- 화면 확인: 앱 화면은 바뀌지 않습니다. README가 GitHub에서 그려진 모습을 실제 Chrome 스크린샷으로 봅니다(T3).
- 일부러 깨뜨려 보기: `test.only`를 남긴 커밋을 CI가 빨간색으로 잡습니다(T1). 버리는 branch에서 하고 지운 뒤, 원래 branch의 CI가 초록인지 다시 봅니다.
