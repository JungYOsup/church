# 계획 스킬(`plan-work`)과 실행 스킬(`run-plan`)

## Context
- 지금 흐름은 `spec-check`가 "큼"으로 판정하면 "plan mode로 계획하고 task로 나눠 진행한다"는 한 줄로 넘깁니다. 계획을 어떻게 세우는지, task를 어떻게 나누고 진행하는지는 비어 있습니다.
- 사용자 결정:
  - 계획과 실행을 **두 스킬로 나눈다**.
  - 실행은 **문제가 없으면 task를 이어서 진행**한다.
  - **문제가 생기면 멈추고 묻지 말고 직접 고쳐서, 앞 task가 확실히 동작한 뒤에만 다음 task로 넘어간다.**
  - **서로 연관된 task라면 앞 task의 동작이 증거로 확인되어야만 뒤 task를 시작한다.** 실패한 task를 둔 채 다음 task로 가는 일은 없다.
  - 시험은 **통계 카드 기능을 실제로 진행하는 것**으로 한다.
- 완성되는 흐름: 요청 → `spec-check`(규모 판정) → 큼이면 `plan-work`(조사 → 계획서 → task 분리 → 승인 → 저장) → `run-plan`(task별 구현 → 확인 → 기록 → 마무리 검증)
- 6축으로는 계획(PL-02 계획 품질), 실행(task 단위 진행), 구조(ST-06 Skill), 개선(IM-02 다섯 번 반복한 절차를 스킬로)에 해당합니다.

## 확인한 사실
- **스킬:** 프로젝트에는 `spec-check`만 있습니다. 계획·실행 스킬은 없습니다.
- **연결할 곳:** `spec-check/SKILL.md`의 61행(큼의 다음 행동)과 93행(예시 3의 "다음"), `CLAUDE.md` 44행(규칙)
- **지금까지 계획서 5개의 공통 틀:** Context / 확인한 사실 / 만들 것 / 검증 / 범위 밖, 그리고 승인 후에 덧붙이는 변경 이력과 검증 결과
- **팀 스킬 참고:**
  - `sizl-start-issue`의 계획서에는 "리스크·의존성" 절이 있어 빌려 옵니다.
  - `sizl-work-on`은 task를 체크박스로 진행하고, 완료할 때 객관적 증거(빌드·테스트 출력)를 요구합니다. 같은 원칙을 씁니다.
  - 이슈·브랜치·PR 단계는 이 프로젝트 흐름(`master`에 직접, 이슈 없음)에 맞지 않아 빼고 가볍게 만듭니다.

## 만들 것

### 1. `.claude/skills/plan-work/SKILL.md` (계획)
- **description:** spec-check가 "큼"으로 판정한 작업, 또는 새 화면·데이터 구조·하네스 동작 변경처럼 여러 단계가 필요한 작업을 구현 전에 계획할 때 쓴다. plan mode에서 조사, 계획서 작성, task 분리, 승인, `docs/plans/` 저장까지 한다. 작음·중간 작업에는 쓰지 않는다.
- **절차:**
  1. **입력:** `spec-check` 보고(spec, 영향 범위, 정한 것, 질문 답)를 이어받습니다. 판정이 없으면 `spec-check`부터 합니다.
  2. **plan mode 진입.**
  3. **조사 → "확인한 사실":** 아래를 추측하지 않고 확인합니다. 조사 결과로 계획이 바뀔 수 있다는 점(지금까지의 실제 사례 4개)을 함께 적습니다.
     - 기존 코드·설정과의 충돌
     - 팀·프로젝트 관례
     - 라이브러리 현재 문서 (Next.js는 설치된 문서, 나머지는 ctx7)
     - `docs/lessons.md`
     - 데이터 계층 규칙
     - 상위 계획서와 참고 디자인
  4. **task 나누기:**
     - 각 task는 끝나면 확인할 수 있어야 합니다(lint·build 통과 + 그 task만의 확인 방법). 확인할 수 없으면 경계가 잘못된 것입니다.
     - 의존 순서대로 놓습니다. 예: 데이터 계층 → 컴포넌트 → 페이지 배치 → 테스트 → 문서·하네스
     - 크기는 확인할 거리가 생기는 최소 단위이고, 대략 파일 1~4개입니다. 파일 단위로 쪼개면 확인할 거리가 없어집니다.
     - 새 화면 동작에는 e2e 테스트 task를 둡니다(DoD).
     - task마다 무엇을 / 파일 / **의존(앞 task 번호)** / 확인 방법을 적습니다.
     - **확인 방법은 "동작한다"를 증명해야 합니다.** lint·build 통과만으로는 부족하고, 그 task의 결과를 직접 보여 주는 증거(테스트 통과, 실행 출력, 화면, 검색 결과)를 정합니다. 뒤 task가 이 증거를 믿고 시작하기 때문입니다.
  5. **계획서 작성:** 아래 틀(`template.md`)을 씁니다.
  6. **승인 요청(ExitPlanMode)** → 승인되면 `docs/plans/YYYY-MM-DD-주제.md`로 저장 → `run-plan`으로 넘김
- **`.claude/skills/plan-work/template.md`:**
  - Context (왜, 6축 위치)
  - 확인한 사실
  - 결정 (spec-check에서 정한 것 + 질문 답)
  - Tasks (`- [ ] T1. … / 파일 / 의존 / 확인(동작 증거)`)
  - 리스크와 멈출 조건
  - 검증 (전체 완료 조건, 일부러 깨뜨려 보기)
  - 범위 밖
  - 변경 이력, 검증 결과 (`run-plan`이 채움)
- **지름길 경고 표:**
  - 조사를 생략하고 바로 계획서 작성
  - 대안을 나열하고 선택을 사용자에게 떠넘김 (추천 하나만)
  - 확인 방법이 없는 task
  - 범위 밖을 비워 두어 작업이 커짐

### 2. `.claude/skills/run-plan/SKILL.md` (실행)
- **description:** 승인된 계획서(`docs/plans/*.md`)의 task를 순서대로 구현, 확인, 기록할 때 쓴다. `plan-work`로 승인받은 직후나 "계획대로 진행해", "이어서 해줘"처럼 계획서가 있는 작업을 실행·재개할 때 쓴다.
- **절차:**
  1. **계획서 찾기:** 방금 승인한 것 → 사용자가 지정한 것 → `docs/plans/` 중 체크 안 된 task가 남은 것
  2. **시작 전:** `git status`(이번 요청 밖의 변경 확인), `nvm use`, 체크 안 된 첫 task부터
  3. **task 반복 (앞 task가 통과해야만 다음 task):**
     - **시작 조건:** 이 task가 의존하는 앞 task의 확인이 통과한 상태인지 봅니다. 그 뒤로 앞 task의 코드가 바뀌었다면 앞 task의 확인을 다시 돌려 통과를 확인한 뒤 시작합니다.
     - 그 task만 구현합니다.
     - **확인:** 그 task의 동작 증거 + `npm run lint && npm run build`를 실행합니다.
       - Stop hook은 응답이 끝날 때만 돌기 때문에, 한 응답에서 여러 task를 진행하면 task 경계에서 직접 돌려야 실패한 task를 바로 알 수 있습니다.
     - **실패하면 직접 고칩니다.** 멈춰서 묻지 않고, 원인을 가설 하나씩 확인하며(동시에 여러 군데 고치지 않음) 확인이 통과할 때까지 고칩니다. 통과하기 전에는 다음 task로 넘어가지 않습니다.
     - 고치다가 앞 task의 코드를 건드렸다면, 그 task의 체크를 풀고 확인을 다시 통과시킵니다(회귀 방지).
     - 통과하면 계획서에 `- [x]`와 증거 한 줄(실행한 명령과 결과)을 적고, 사용자에게 한 줄로 진행을 보고한 뒤 다음 task로 이어서 진행합니다.
  4. **사용자에게 묻는 경우는 "고치는 방법이 계획 밖의 결정일 때"뿐:**
     - 고치려면 계획의 범위·화면 구성·데이터 구조를 바꿔야 할 때
     - 새 의존성 추가, 되돌리기 어려운 작업이 필요할 때
     - 영향 범위가 계획보다 커져 재판정이 필요할 때
     - 이때도 다음 task로 넘어가지 않습니다. 상황, 선택지, 추천을 보고하고 답을 받아 고친 뒤 이어갑니다.
  5. **계획과 달라진 점:** 계획서 `## 변경 이력`에 날짜·내용·이유를 적습니다.
  6. **마무리:**
     - 계획서의 검증 절 실행(`npm run test`, 375/768/1440px 화면, 일부러 깨뜨려 보기)
     - `## 검증 결과`에 실제 출력 근거와 함께 기록
     - 독립 리뷰(`/code-review`)
     - 새 함정은 `docs/lessons.md`에 추가
     - 완료 보고에서 커밋 여부를 묻습니다(커밋은 요청할 때만).
- **지름길 경고 표:**
  - "앞 task는 나중에 고치고 일단 다음 task부터" → 깨진 기반 위에 쌓여 원인을 찾기 어려워짐. 앞 task를 먼저 통과시킴
  - "막혔으니 사용자에게 넘김" → 고치는 것이 기본. 계획 밖 결정이 필요할 때만 물음
  - task 여러 개를 한꺼번에 구현 → 실패 원인을 찾기 어려움
  - 확인 없이 체크, lint·build만 통과했다고 "동작한다"고 체크
  - 계획과 다르게 했는데 기록 생략
  - 막혔는데 계획을 조용히 바꿈
  - 출력 없이 "통과"라고 보고

## 리스크와 멈출 조건
- **트리거 겹침:** `spec-check`와 `plan-work`의 description이 겹치면 순서가 꼬일 수 있습니다. 그래서 `plan-work` description에 "spec-check가 큼으로 판정한 뒤"를 분명히 적습니다.
- **두 스킬 사이의 틈:** 계획서 형식이 바뀌면 `run-plan`이 task를 못 찾을 수 있습니다. 그래서 task 형식(`- [ ] T1.`)을 `template.md` 한 곳에서 정하고 두 스킬이 같이 가리킵니다.
- **고치기를 끝없이 반복할 위험:** 같은 원인을 맴돌 수 있습니다. 그래서 가설을 하나씩 확인하고, 시도한 가설과 결과를 계획서 변경 이력에 적어 같은 시도를 되풀이하지 않게 합니다. 원인이 계획 밖 결정으로 드러나면 그때 묻습니다.
