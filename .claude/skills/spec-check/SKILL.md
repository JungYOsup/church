# spec-check: 요청의 진짜 크기를 재고 작업 방식을 고른다

요청 문장의 크기와 실제 변경의 크기는 다르다. "메뉴의 '행사'를 '행사 안내'로 바꿔줘"는 한 줄짜리 요청이지만, 이 프로젝트에서는 메뉴 목록, e2e 테스트의 메뉴 명세, 페이지 제목에 걸려 있다. 메뉴만 고치면 커밋할 때 pre-commit hook이 테스트 실패로 커밋을 거부한다. 반대로 거창해 보이는 요청이 파일 하나로 끝나기도 한다.

그래서 요청 문장만 보고 판단하지 말고, **영향 범위를 먼저 찾은 뒤** 규모를 판정한다. 판정에 따라 작업 방식이 달라진다. 작은 일은 절차 없이 빨리 끝내고, 큰 일은 계획을 세워 실수를 막는다.

## 절차

### 1. spec 정리
요청을 세 줄로 다시 쓴다. 이 세 줄이 흐릿하면 요구사항이 모호하다는 신호다.
- **무엇을:** 바꾸려는 것 (예: 메뉴 이름 "행사" → "행사 안내")
- **어디서:** 사용자가 말한 위치 (예: 상단 메뉴)
- **완료 조건:** 끝났다고 판단할 기준 (예: 데스크톱·모바일 메뉴에 새 이름이 보이고 `npm run test` 통과)

### 2. 영향 범위 조사
요청에 비례해서 조사한다. 문구 하나면 검색 한두 번으로 충분하고, 새 기능이면 관련 폴더를 훑는다. 확인할 곳은 다음과 같다.
- **같은 문자열·식별자:** `grep -rn '<문자열>' src e2e`. 같은 단어가 다른 뜻으로 쓰인 곳은 제외한다(예: 히어로의 "행사와 소식"은 메뉴가 아님).
- **테스트:** `e2e/`가 그 문구나 동작을 기대값으로 적고 있는지. 테스트는 기대값을 직접 적기 때문에 함께 바꿔야 한다.
- **페이지 제목·metadata:** `src/app/**/page.tsx`의 `metadata`와 화면 제목
- **데이터 계층:** 데이터가 필요하면 `src/lib/data`, `src/lib/mock`, `src/lib/types.ts`. 컴포넌트는 데이터 계층을 거쳐야 한다는 규칙이 있다.
- **하네스:** `CLAUDE.md`, `.claude/`(settings, hooks, skills), `.husky/`, `docs/plans/`
- **배운 점:** `docs/lessons.md`에 관련 함정이 있는지
- **이번 요청 밖의 변경:** `git status`로 이번 요청과 관계없이 커밋되지 않은 변경이 있는지 본다. 지금 대화에서 앞서 만든 것인지, 다른 세션이 남긴 것인지 구분해서 적는다. 이번 작업에 섞지 않고, 그 변경을 커밋하거나 근거로 삼을 때는 그 변경이 말하는 결과(파일, 아티팩트)가 실제로 있는지 먼저 확인한다.

### 3. 모호한 점 질문
조사하다 보면 요청이 정하지 않은 선택지가 드러난다. **결과가 달라지는 것만** 묻는다. 예: "메뉴 이름만 바꿀까요, 행사 페이지 제목(탭 제목)도 바꿀까요?" 답이 정해져 있거나, 관례나 계획서를 따르면 되거나, 나중에 쉽게 바꿀 수 있는 것은 묻지 않고 정해서 보고의 "정한 것"에 적는다. 질문이 많으면 사용자가 답하느라 지치고, 정말 중요한 질문이 묻힌다. 질문은 보통 1~2개면 충분하다.

### 4. 규모 판정
아래 표에서 기준마다 해당하는 칸을 고르고, **가장 큰 쪽을 따른다.** 하나라도 "큼"이면 큼이다.

| 기준 | 작음 | 중간 | 큼 |
|---|---|---|---|
| 동작 | 그대로 (문구, 색, 오타) | 그대로이거나 작은 조정 | 새 화면·동작, 데이터 구조 |
| 영향 범위 | 1~2곳이고 다 찾음 | 3~5곳, 또는 테스트 수정이 함께 필요 | 여러 영역, 또는 범위를 다 찾지 못함 |
| 모호함 | 없음 | 질문 1~2개로 해결 | 요구사항 자체를 정해야 함 |
| 의존성·설정 | 없음 | 없음 | 새 라이브러리, 빌드·테스트 설정 변경 |
| 하네스 | 안 건드림 | 문구만 고침 | hook·권한·규칙의 동작 변경 |
| 되돌리기 | 쉬움 | 쉬움 | 어려움 (데이터, 배포, 외부 서비스) |

### 5. 판정 보고
아래 형식으로 짧게 보고한다. 사용자가 판정이 맞는지 한눈에 보고 바로잡을 수 있게 하기 위함이다.

```
**spec** 무엇을: … / 어디서: … / 완료 조건: …
**영향 범위** 파일 N곳: `경로` (이유), …  ·  제외: `경로` (이유)
**확인할 점** (없으면 "없음")
**정한 것** 묻지 않고 판단한 세부 사항과 이유 (없으면 줄 생략)
**판정** 작음|중간|큼 — 표에서 걸린 기준 한 줄
**다음** 바로 수정 | 짧은 계획 확인 | plan-work로 계획
```

### 6. 판정에 따른 다음 행동
- **작음:** 보고하고 바로 수정한다. 확인할 점이 없으면 승인을 기다리지 않는다. lint·build는 Stop hook이, 테스트는 커밋할 때 pre-commit hook이 확인한다. 요청받지 않은 문서 수정(계획서 변경 이력 등)을 끼워 넣지 않는다.
- **중간:** 3~5줄짜리 계획(바꿀 파일과 순서, 확인 방법)을 보여 주고 확인을 받은 뒤 진행한다. 계획서 파일은 만들지 않는다.
- 작음·중간에서 계획서 변경 이력은 **계획서에 적힌 결정(구조, 스택, 범위, 화면 구성)이 바뀔 때만** 적는다. 문구나 이름 같은 작은 변경은 커밋 메시지로 충분하다. 작은 일에 기록 절차를 덧붙이면 절차가 작업보다 커진다.
- **큼:** `plan-work` 스킬로 넘긴다. plan mode에서 조사하고 확인 가능한 task로 나눈 계획서를 승인받아 `docs/plans/`에 저장한다. 그다음 `run-plan` 스킬이 앞 task가 동작함을 확인하며 하나씩 진행한다. 이 보고의 spec, 영향 범위, 정한 것, 질문 답이 계획의 입력이 된다.

### 7. 진행 중 재판정
작음·중간으로 시작했는데 예상하지 못한 파일이 더 걸리거나 새 질문이 생기면, 그 자리에서 멈추고 다시 판정해 알린다. 판정은 처음 한 번으로 끝나는 것이 아니라 작업 내내 맞는지 확인하는 것이다.

## 예시

**예시 1: "메뉴의 '행사'를 '행사 안내'로 바꿔줘"**
```
**spec** 무엇을: 메뉴 이름 "행사" → "행사 안내" / 어디서: 상단·모바일 메뉴 / 완료 조건: 두 메뉴에 새 이름, npm run test 통과
**영향 범위** 파일 3곳: `src/lib/navigation.ts` (메뉴 목록), `e2e/navigation.spec.ts` (메뉴 명세·탭 제목 테스트), `src/app/events/page.tsx` (페이지·탭 제목)  ·  제외: `HeroBanner.tsx`의 "행사와 소식" (메뉴 아님)
**확인할 점** 페이지 제목(탭 "행사 | 함께하는 교회")도 바꿀까요?
**판정** 중간 — 테스트 수정이 함께 필요하고 질문 1개
**다음** 답을 받으면 짧은 계획 확인
```

**예시 2: "히어로 설명의 '연합을'을 '연합을 함께'로 고쳐줘"**
```
**spec** 무엇을: 히어로 설명 문구 수정 / 어디서: 홈 히어로 / 완료 조건: 문구가 바뀌고 lint·build 통과
**영향 범위** 파일 1곳: `src/components/home/HeroBanner.tsx`  ·  e2e는 이 문구를 검사하지 않음
**확인할 점** 없음
**판정** 작음 — 문구만, 1곳
**다음** 바로 수정
```

**예시 3: "교회 상세 페이지 만들어줘"**
```
**spec** 무엇을: 교회 상세 페이지(소개, 목사, 인원, 태그) / 어디서: `/churches/[id]` / 완료 조건: 목데이터 교회마다 상세 페이지가 열리고, 없는 id는 404, e2e 테스트 추가 후 통과
**영향 범위** 새 라우트(`src/app/churches/[id]/page.tsx`), 데이터 계층(`src/lib/types.ts`의 Church, `src/lib/mock/churches.ts`, `src/lib/data/churches.ts`), 새 컴포넌트(`src/components/church/`), `e2e/`  ·  제외: 메뉴(상세 페이지는 메뉴에 없음)
**확인할 점** 교회의 행사·공지 목록도 이번에 넣을까요? (행사·공지 데이터가 아직 없음)
**정한 것** 교회 목데이터는 상위 계획서대로 서울·경기 12~20곳, 없는 id는 Next의 notFound()로 404 처리
**판정** 큼 — 새 화면·새 데이터 구조
**다음** plan-work로 계획
```

## 지름길 경고
이런 생각이 들면 멈추고 절차로 돌아간다.

| 이런 생각 | 실제로 일어나는 일 | 대신 할 일 |
|---|---|---|
| "이름만 바꾸면 되니 검색은 생략" | 테스트 명세가 옛 이름이라 커밋이 거부됨 | 같은 문자열을 `src`와 `e2e`에서 검색 |
| "작은 일이니 물어볼 것 없음" | 사용자가 원한 범위와 달라 다시 고침 | 결과가 달라지는 선택지는 묻기 |
| "빨리 하려고 큼을 중간으로" | 계획 없이 여러 파일을 고치다 되돌림 | 표에서 가장 큰 기준을 따르기 |
| "한 줄이라 하네스도 작음" | hook·권한의 동작이 바뀌어 검증이 약해짐 | 동작이 바뀌면 큼 |
| "다른 세션이 남긴 변경도 같이 커밋" | 사실과 다른 내용이 기록됨 | 그 변경이 말하는 결과가 실제로 있는지 확인 |
| "꼼꼼하게 하려고 작은 일에도 계획서·문서를 같이 고침" | 절차가 작업보다 커지고 기록이 잡음이 됨 | 계획서의 결정이 바뀔 때만 기록 |
| "혹시 모르니 이것도 물어보자" | 질문이 쌓여 중요한 질문이 묻힘 | 결과가 달라지는 것만 묻고 나머지는 "정한 것"에 적기 |
