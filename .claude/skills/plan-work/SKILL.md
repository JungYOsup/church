# plan-work: 큰 작업을 조사하고 확인 가능한 task로 나눈다

큰 작업이 틀어지는 가장 흔한 이유는 확인하지 않은 가정이다. 이 프로젝트에서도 계획 단계의 조사로 방향이 바뀐 일이 여러 번 있었다.
- `create-next-app`이 기존 파일과 충돌해서, 임시 폴더에서 생성해 복사하는 방식으로 바꿨다.
- Playwright가 요구하는 브라우저 버전이 달라서, 설치된 Chrome을 쓰기로 했다.
- `next dev`는 한 프로젝트에 두 개를 띄울 수 없어서, 테스트는 빌드 결과를 3100 포트로 띄우기로 했다.
- 팀이 husky를 쓰고 있어서, git hook 도구를 husky로 맞췄다.

그래서 계획은 조사에서 시작하고, 구현은 하나씩 확인할 수 있는 task로 나눈다. 실행은 `run-plan` 스킬이 맡는다. 앞 task가 동작함을 증거로 확인해야만 다음 task로 넘어가기 때문에, **task마다 "동작한다"를 증명하는 확인 방법이 있어야 한다.**

## 절차

### 1. 입력 확인
`spec-check` 보고(spec, 영향 범위, 확인할 점의 답, 정한 것)를 이어받는다. 판정을 하지 않았다면 `spec-check`부터 한다. 질문의 답이 아직 없으면 답을 받은 뒤 시작한다.

### 2. plan mode 진입
plan mode에서는 계획 파일 말고는 아무것도 고치지 않는다. 조사는 읽기와 검색으로만 한다.

plan mode의 기본 안내(탐색 에이전트로 조사하고 설계 에이전트로 계획)는 이 스킬의 3~5단계가 대신한다. 이 프로젝트의 작업은 대부분 파일 위치를 이미 알고 있어 직접 읽는 편이 빠르다. 여러 폴더를 훑어야 하거나 위치를 모를 때만 탐색 에이전트를 쓴다.

### 3. 조사 → "확인한 사실"
추측하지 말고 확인한다. 확인할 것은 다음과 같다.
- **기존 코드·설정과의 충돌:** 새로 만들 것이 이미 있는지, 덮어쓰게 되는 설정은 없는지
- **팀·프로젝트 관례:** 같은 일을 이미 하는 방식(폴더 구조, 데이터 계층, 테스트 위치, 팀 워크플로)
- **라이브러리 현재 문서:** Next.js는 `node_modules/next/dist/docs/`, 나머지(Tailwind v4, shadcn/ui, 카카오맵, Supabase 등)는 ctx7
- **`docs/lessons.md`:** 이번 작업과 관련된 함정
- **데이터 계층 규칙:** 데이터가 필요하면 `src/lib/types.ts` → `src/lib/mock/` → `src/lib/data/` 순서로 만들고 컴포넌트는 `src/lib/data/`만 쓴다
- **상위 계획서와 참고 디자인:** `docs/plans/2026-09-30-church-community.md`에서 이번 작업과 관련된 절(라우트, 화면 구성, 디자인 토큰, 데이터 계층 등)을 **통째로 읽고**, 그 절이 이미 정한 결정(이름, 위치, 색·토큰, 열 수)을 확인한 사실에 옮긴다. 낱말로만 검색하면 결정이 제목 줄에 있을 때 놓친다. 통계 카드 때 "통계"로만 검색해서 "디자인 토큰(`globals.css`의 `@theme`)" 절의 결정을 놓쳤고, 리뷰에서야 잡혔다. 참고 이미지는 Read 도구로 직접 본다(Bash로는 `~/Downloads`를 읽지 못한다).

확인한 사실은 출처와 함께 적는다. 조사로 계획이 바뀌었다면 그 점도 적는다.

### 4. task 나누기
좋은 task는 끝났을 때 "됐다"를 증거로 보여 줄 수 있다. 다음 기준으로 나눈다.
- **확인할 수 있는 단위:** 각 task가 끝나면 lint·build가 통과하고, 그 task만의 동작 증거가 있어야 한다. 확인할 거리가 없으면 경계가 잘못된 것이니 앞뒤 task와 합친다.
- **동작 증거는 구체적으로:** lint·build 통과만으로는 "동작한다"고 할 수 없다. 테스트 통과, 실행 출력, 화면, 검색 결과처럼 그 task의 결과를 직접 보여 주는 확인 방법과 기대 결과를 적는다. 뒤 task는 이 증거를 믿고 시작한다. 자주 쓰는 방법은 다음과 같다.
  - **화면이 없는 데이터 함수:** 이미 설치된 jiti로 임시 스크립트를 실행해 반환값을 출력한다. `JITI_ALIAS='{"@":"<프로젝트>/src"}' npx jiti <스크립트>`처럼 별칭은 접두어 꼴로 준다(`@/*` 꼴은 모듈을 찾지 못한다).
  - **화면:** DoD대로 `npm run dev`(3000)를 띄워 375 / 768 / 1440px에서 본다. 3100 포트는 `npm run test`가 빌드 서버를 띄우는 자리라(`reuseExistingServer: false`) 확인용 서버를 따로 띄우지 않는다.
- **의존 순서:** 앞 task 위에 쌓이도록 놓는다. 보통 데이터 계층 → 컴포넌트 → 페이지 배치 → 테스트 → 문서·하네스 순서다. task마다 의존하는 앞 task 번호를 적는다.
- **크기:** 확인할 거리가 생기는 가장 작은 단위로, 대략 파일 1~4개다. 파일 하나씩 쪼개면 확인할 것이 없어지고, 너무 크면 실패했을 때 원인을 찾기 어렵다.
- **테스트:** 새 화면 동작에는 `e2e/`에 테스트를 추가하는 task를 둔다(CLAUDE.md DoD). 테스트 기대값은 앱 코드에서 가져오지 않고 직접 적는다.

### 5. 계획서 작성
같은 폴더의 `template.md` 틀을 그대로 쓴다. 특히 Tasks 절의 형식(`- [ ] **T1. …**`, 파일·의존·확인)은 `run-plan`이 읽으므로 바꾸지 않는다. 방법은 추천하는 것 하나만 적는다. 대안 목록을 늘어놓고 고르게 하면 승인하는 사람이 설계를 떠안게 된다.

### 6. 승인과 저장
- ExitPlanMode로 승인을 요청한다.
- 승인되면 계획을 `docs/plans/YYYY-MM-DD-<주제>.md`로 저장한다.
- 이어서 `run-plan` 스킬로 실행한다.

## 예시: "다가오는 행사" 섹션의 task
```
- [ ] **T1. 행사 데이터 계층**
  - 파일: `src/lib/types.ts`, `src/lib/mock/events.ts`, `src/lib/data/events.ts`
  - 의존: 없음
  - 확인(동작 증거): `getUpcomingEvents(3)`가 날짜순으로 3개를 돌려준다. jiti로 실행한 임시 스크립트 출력으로 순서와 개수 확인
- [ ] **T2. EventCard·UpcomingEvents 컴포넌트와 홈 배치**
  - 파일: `src/components/event/EventCard.tsx`, `src/components/home/UpcomingEvents.tsx`, `src/app/page.tsx`
  - 의존: T1
  - 확인(동작 증거): 개발 서버 홈에서 섹션 제목과 카드 3개가 보이고, 375/768/1440px에서 페이지 가로 스크롤이 없다
- [ ] **T3. e2e 테스트**
  - 파일: `e2e/home.spec.ts`
  - 의존: T2
  - 확인(동작 증거): `npm run test`에서 새 테스트를 포함해 전부 통과. 목데이터의 행사 제목을 바꾸면 새 테스트가 실패
```

## 지름길 경고
| 이런 생각 | 실제로 일어나는 일 | 대신 할 일 |
|---|---|---|
| "아는 내용이니 조사는 생략" | 버전 차이나 기존 설정 충돌로 구현 중에 계획이 무너짐 | 확인한 사실을 출처와 함께 적기 |
| "상위 계획서는 낱말 검색으로 충분" | 제목 줄에 있는 결정(디자인 토큰 등)을 놓쳐 리뷰에서야 잡힘 | 관련 절을 통째로 읽고 결정을 옮겨 적기 |
| "선택지를 보여 주고 고르게 하자" | 설계 판단을 사용자에게 떠넘김 | 추천 하나와 이유를 적기 |
| "파일마다 task 하나씩" | 확인할 거리가 없는 task가 생김 | 동작 증거가 생기는 단위로 묶기 |
| "확인은 lint·build면 충분" | 동작하지 않는 코드가 다음 task의 기반이 됨 | 그 task의 결과를 보여 주는 증거를 정하기 |
| "범위 밖은 굳이 안 적어도" | 작업이 슬금슬금 커짐 | 하지 않을 것을 적기 |
