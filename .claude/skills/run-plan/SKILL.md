# run-plan: task를 하나씩, 확실히 동작시키며 진행한다

연관된 task는 앞 task 위에 쌓인다. 앞 task가 깨진 채로 다음 task를 진행하면, 나중에 문제가 생겼을 때 원인이 어느 task에 있는지 찾기 어렵고 고칠 범위도 커진다. 그래서 이 스킬의 원칙은 하나다.

> **앞 task가 동작함을 증거로 확인해야만 다음 task로 넘어간다. 실패하면 멈추고 넘기지 말고 직접 고쳐서 통과시킨다.**

문제가 없으면 task마다 확인을 받으러 멈추지 않고 이어서 진행한다. 계획은 이미 승인받았기 때문이다.

## 절차

### 1. 계획서 찾기
다음 순서로 찾는다.
1. 방금 `plan-work`로 승인받은 계획서
2. 사용자가 지정한 계획서
3. `docs/plans/` 중 체크하지 않은 task(`- [ ]`)가 남은 계획서

task 형식은 `.claude/skills/plan-work/template.md`의 Tasks 절을 따른다.

### 2. 시작 전 점검
- `git status`로 이번 계획과 관계없이 커밋되지 않은 변경이 있는지 본다. 있으면 섞지 않는다.
- `nvm use`로 Node 22로 바꾼다.
- 체크하지 않은 첫 task부터 시작한다. 재개하는 경우, 마지막으로 체크한 task의 확인을 한 번 다시 돌려 지금도 통과하는지 본다.

### 3. task 하나씩 진행
각 task마다 아래 순서를 지킨다.

1. **시작 조건 확인:** 이 task가 의존하는 앞 task가 체크되어 있는지 본다. 체크한 뒤에 앞 task의 코드가 바뀌었다면, 앞 task의 확인을 다시 돌려 통과한 다음 시작한다.
2. **테스트 먼저(red):** 계획서의 "테스트 먼저"대로 테스트를 먼저 쓰고 실행해 실패를 본다.
   - 실패 이유가 "구현이 없어서"인지 확인한다. 파일이 없어서 나는 오류(모듈을 찾지 못함, 명령 없음)는 설정이나 경로 문제와 구분되지 않는다. 그래서 함수 모양만 있는 빈 구현을 두고 다시 돌려, 기대한 테스트만 실패하는지 본다.
   - red 출력 한 줄을 증거로 남긴다.
   - `해당 없음`이면 건너뛴다. 이 항목이 없는 예전 계획서는 동작 증거에 적힌 테스트를 먼저 쓴다.
   - `src/lib` 로직은 짝 테스트(`<이름>.test.ts`) 없이 구현 파일을 쓰면 PreToolUse hook이 막는다.
3. **이 task만 구현한다.** 테스트가 통과(green)하도록 구현하고, 다음 task의 일을 미리 섞지 않는다. 섞으면 실패했을 때 원인을 가르기 어렵다.
4. **확인:** 계획서에 적힌 이 task의 동작 증거를 실행하고, `npm run lint && npm run build`를 함께 돌린다. Stop hook은 응답이 끝날 때만 돌기 때문에, 한 응답에서 여러 task를 진행할 때는 task 경계에서 직접 돌려야 어느 task에서 깨졌는지 바로 알 수 있다. 화면은 `npm run dev`(3000)로 띄워 본다. 3100 포트는 `npm run test`가 쓰므로 확인용 서버를 띄우지 않는다.
5. **실패하면 직접 고친다:**
   - 멈춰서 사용자에게 넘기지 않는다. 고치는 것이 기본이다.
   - 원인은 가설 하나씩 확인한다. 동시에 여러 군데를 고치면 무엇이 효과가 있었는지 알 수 없다.
   - 같은 시도를 되풀이하지 않도록, 시도한 가설과 결과를 기억해 두고 필요하면 계획서 변경 이력에 적는다.
   - 낯선 오류는 `docs/lessons.md`부터 확인한다. 라이브러리 동작이 의심되면 문서(Next.js는 설치된 문서, 나머지는 ctx7)로 확인한다.
   - 고치다가 앞 task의 코드를 건드렸다면, 그 task의 체크를 풀고 확인을 다시 통과시킨다.
   - **통과하기 전에는 다음 task로 넘어가지 않는다.**
6. **기록:** 통과하면 계획서의 체크를 `- [x]`로 바꾸고, 그 아래에 증거(red 출력, green 결과, 실행한 명령)를 적는다.
7. **보고하고 이어서:** 사용자에게 한 줄로 알린다(예: "T1 데이터 계층 완료 — `getStats()`가 4개 값 반환, lint·build 통과"). 그리고 다음 task로 이어서 진행한다.

### 4. 사용자에게 묻는 경우
고치는 것이 기본이지만, **고치는 방법이 계획 밖의 결정일 때는** 사용자가 정해야 한다.
- 고치려면 계획의 범위, 화면 구성, 데이터 구조를 바꿔야 할 때
- 새 의존성을 추가하거나 되돌리기 어려운 작업(데이터, 배포, 외부 서비스)이 필요할 때
- 영향 범위가 계획보다 커져 다시 판정해야 할 때

이때도 다음 task로 넘어가지 않는다. 상황, 선택지, 추천을 짧게 보고하고, 답을 받아 고친 뒤 이어간다.

### 5. 계획과 달라진 점
계획과 다르게 한 것은 계획서 `## 변경 이력`에 날짜, 내용, 이유를 적는다. 조용히 바꾸면 계획서와 실제가 어긋나 다음 세션이 잘못된 정보를 믿게 된다.

### 6. 마무리
모든 task를 체크한 뒤 다음을 한다.
- 계획서의 검증 절을 실행한다: `npm run test`, `npm run dev`에서 375 / 768 / 1440px 화면 확인, 일부러 깨뜨려 보기
- **일부러 깨뜨려 보기**는 체크한 task의 코드를 잠깐 바꾸는 일이다. 테스트가 잡아내는 것을 확인하면 바로 되돌리고, `npm run test`를 다시 돌려 원래 상태가 통과하는지 본다. 이렇게 되돌린 것은 task의 체크를 풀지 않는다.
- 결과를 계획서 `## 검증 결과`에 실제 출력과 함께 적는다. 출력 없이 "통과"라고만 쓰지 않는다.
- `/code-review`로 구현과 분리된 리뷰를 받는다. 지적마다 문서, 측정, 재현으로 사실인지 확인하고, 확인된 것만 고친다.
  - 고친 코드가 체크한 task에 걸치면, 그 task의 체크를 풀고 동작 증거를 다시 통과시킨 뒤 다시 체크한다(3단계 5번과 같은 규칙). 마무리 단계라고 재확인을 건너뛰지 않는다.
  - 반영한 것은 `## 변경 이력`에, 반영하지 않은 지적은 이유와 함께 `## 검증 결과`에 적는다.
- 이번에 걸려 넘어진 새 함정은 `docs/lessons.md`에 추가한다.
- 완료 보고를 하고 커밋 여부를 묻는다. 커밋은 사용자가 요청할 때만 한다. 커밋할 때 pre-commit hook이 lint와 테스트를 다시 돌린다.

|---|---|---|
| "앞 task는 나중에 고치고 일단 다음 task부터" | 깨진 기반 위에 쌓여 원인을 찾기 어려워짐 | 앞 task를 먼저 통과시키기 |
| "막혔으니 사용자에게 넘기자" | 고칠 수 있는 문제로 사용자를 기다리게 함 | 직접 고치기. 계획 밖 결정만 묻기 |
| "빠르게 task 두세 개를 한꺼번에" | 실패하면 어느 task 문제인지 모름 | 한 task씩 구현하고 확인 |
| "lint·build가 통과했으니 체크" | 동작하지 않는 코드가 다음 task의 기반이 됨 | 계획서의 동작 증거까지 확인 |
| "간단하니 구현부터, 테스트는 나중에" | 구현에 맞춰 쓴 테스트라 잘못을 잡는지 알 수 없음 | 테스트를 먼저 쓰고 red를 본 뒤 구현 |
| "계획과 조금 다르지만 기록은 생략" | 계획서와 실제가 어긋남 | 변경 이력에 적기 |
| "여러 군데를 한 번에 고쳐 보자" | 무엇이 효과가 있었는지 모름 | 가설 하나씩 확인 |
| "통과했다고만 보고" | 근거가 없어 확인할 수 없음 | 실행한 명령과 결과를 함께 보고 |
| "리뷰 반영은 마무리라 다시 확인할 것 없음" | 체크한 task의 증거가 고친 코드와 어긋남 | 걸친 task의 체크를 풀고 다시 확인 |
